# Discipline Conformance Assessment

The `bin/verification_process/discipline_verify` script checks whether a repository satisfies the requirements of the declared discipline. The script reads `results/*.json` reports prepared by standard jobs, builds the final `conformance.json` report, and returns the exit code used by the pipeline quality gate.

This is the final stage of the verification process. The script result says whether the required standards were satisfied, whether only accepted waivers exist, or whether the pipeline should be blocked.

## Usage

By default, the script reads reports from the `results/` directory and writes `conformance.json`:

```bash
bin/verification_process/discipline_verify
```

Specify the reports directory:

```bash
bin/verification_process/discipline_verify --results-dir results
```

Specify the output file:

```bash
bin/verification_process/discipline_verify --output conformance.json
```

Specify the discipline declaration file:

```bash
bin/verification_process/discipline_verify --discipline-file discipline.yaml
```

Full example:

```bash
bin/verification_process/discipline_verify \
  --results-dir results \
  --discipline-file discipline.yaml \
  --output conformance.json
```

Help:

```bash
bin/verification_process/discipline_verify --help
```

## Requirements

The script requires:

- Python 3,
- JSON reports generated by standard jobs.

The script does not require `yq`. It does not validate the `discipline.yaml` contract; that step is handled by `bin/verification_process/discipline_validate`.

## Environment Variables

If arguments are not provided, the script uses default values and environment variables:

| Variable | Meaning | Default value |
| --- | --- | --- |
| `CONFORMANCE_FILE` | output file for the discipline QA report | `conformance.json` |
| `DISCIPLINE_FILE` | path to the team's declaration | `discipline.yaml` |
| `CI_PIPELINE_ID` | GitLab pipeline identifier | empty |
| `CI_PIPELINE_SOURCE` | GitLab pipeline source | empty |
| `CI_COMMIT_REF_NAME` | pipeline ref | empty |
| `CI_COMMIT_SHA` | commit SHA | empty |
| `CI_PIPELINE_URL` | pipeline URL | empty |

The `CI_*` variables are written to the `pipeline` section in `conformance.json`.

## Input

The script reads all files:

```text
results/*.json
```

Minimal standard report:

```json
{"key":"STD-REPO-001","status":"pass"}
```

Standard report with a failure:

```json
{"key":"STD-REPO-003","status":"fail"}
```

Standard report with an active waiver:

```json
{"key":"STD-REPO-002","status":"waived","exception":{"check":"STD-REPO-002","reason":"repository is being migrated","owner":"platform-team","expires":"2026-09-30"}}
```

Required fields in a standard report:

| Field | Meaning |
| --- | --- |
| `key` | standard or check identifier |
| `status` | standard result: `pass`, `fail`, or `waived` |

The `exception` field is optional. It should exist for the `waived` status.

## Output

The script writes:

```text
conformance.json
```

The same JSON is also printed to standard output so the result is visible in the job log.

Example structure:

```json
{

    "source": "merge_request_event",
    "ref": "feature/example",
    "sha": "abc123",
    "url": "https://gitlab.example/pipelines/123"
  },
  "summary": {
    "total": 2,
    "passed": 1,
    "waived": 1,
    "failed": 0,
    "errors": 0
  },

    {

      "key": "STD-REPO-001",

```

## Overall Verification Status

The script calculates the final status based on standard reports:

| Status | Condition |
| --- | --- |
| `pass` | reports exist and all checks have status `pass` |
| `pass_with_waivers` | there is no `fail`, but at least one check has status `waived` |
| `fail` | at least one check has status `fail` |
| `error` | at least one report cannot be read or does not contain `key` / `status` |
| `no_checks` | the results directory does not contain any `*.json` file |

The `fail` status takes precedence over `waived`. If there is at least one fail without an active waiver, the quality gate blocks the pipeline.

## Exit Codes

| Code | Status | Meaning |
| --- | --- | --- |
| `0` | `pass` | all standards passed |
| `101` | `pass_with_waivers` | there are non-conformances, but they are covered by active waivers |
| `1` | `fail`, `error`, `no_checks` | the pipeline should be blocked |

In GitLab CI, the aggregation job should allow code `101`:

```yaml
allow_failure:
  exit_codes:
    - 101
```

This makes the waiver visible as debt, but it does not block the pipeline.

## Client Messages

After writing `conformance.json`, the script prints a verdict that is readable in the job log.

Success:

```text
✅ Bramka jakości dyscypliny: OK. Wszystkie wymagane standardy przeszły.
```

Success with a waiver:

```text
⚠️ Bramka jakości dyscypliny: OK z odstępstwem. Niezgodności są objęte ważnym odstępstwem.
- STD-REPO-002: odstępstwo do 2026-09-30; właściciel: platform-team; powód: repozytorium jest w trakcie migracji
```

Block:

```text
❌ Bramka jakości dyscypliny: BLOKADA. Wykryto niezgodności bez ważnego odstępstwa.
- STD-REPO-003: results/STD-REPO-003.json
```

Aggregation error:

```text
❌ Bramka jakości dyscypliny: BŁĄD AGREGACJI. Nie udało się odczytać części raportów.
```

No checks:

```text
❌ Bramka jakości dyscypliny: BRAK CHECKÓW. Nie znaleziono raportów results/*.json.
```

## Place in the Process

`bin/verification_process/discipline_verify` should be run after standard jobs finish:

1. `bin/verification_process/discipline_validate` validates `discipline.yaml`.
2. Standard jobs write `results/{STD_ID}.json`.
3. `bin/verification_process/discipline_verify` aggregates results into `conformance.json`.
4. The script exit code controls the pipeline quality gate.

In the example GitLab pipeline, the script is fetched from the central discipline repository:

```bash
curl -fsSL "$verify_url" -o .discipline_verify
chmod +x .discipline_verify
set +e
./.discipline_verify \
  --results-dir results \
  --discipline-file "$DISCIPLINE_FILE" \
  --output "$CONFORMANCE_FILE"
verify_rc=$?
set -e

echo "discipline_verify exit code: ${verify_rc}"
exit "$verify_rc"
```

`conformance.json` is a CI artifact. It should not be committed to the application repository.
